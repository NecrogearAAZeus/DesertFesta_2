## 1. 조사 결과

### 1.1 matter.js

| 항목 | 내용 |
|---|---|
| 버전 | 최신 0.20.0, 마지막 배포 2024-06, MIT (확인: `npm view matter-js`) |
| Node에서 렌더러 없이 | `Engine.create()` → `Composite.add()` → `Engine.update(engine, dt)`를 직접 반복하면 된다. Render/Runner가 필요 없다 (확인: `sim.js`가 Node 24에서 이대로 동작) |
| 고정 timestep | `Engine.update(engine, delta)`, 기본값 16.666ms. Runner 문서는 delta를 60Hz 이하(≤16.666ms)로 두고 실행 중에 바꾸지 말라고 한다 (확인: 문서). 서버에서는 Runner 없이 `for` 루프로 같은 dt를 넣으면 된다 |
| 기본값 | `positionIterations` 6, `velocityIterations` 4, `enableSleeping` false, `gravity.scale` 0.001 (확인: Engine 문서) |
| 바디 기본값 | `restitution` 0 (두 바디 중 큰 값 사용), `friction` 0.1 (작은 값 사용), `frictionAir` 0.01, `frictionStatic` 0.5, `density` 0.001, `slop` 0.05 (확인: Body 문서) |
| 센서 | `isSensor: true`는 충돌 이벤트만 내고 밀어내지 않는다 (확인: 문서). 프로토타입은 회전 없는 사각형이라 센서 바디 없이 `abs(dx)<w/2 && abs(dy)<h/2`로 판정했다. 이쪽이 더 단순하다 |
| 터널링(관통) | CCD 없음. 이슈 #5는 아직 열려 있다. 작성자 권장: ① 서브스텝(작은 dt를 여러 번, 예: 120Hz) ② 얇은 벽을 두껍게(그림은 얇게) ③ 최대 속도 제한 ④ 속도 방향 레이캐스트 (확인: GitHub 이슈 #5) |
| 값 감각 | 문서의 기본값을 그대로 쓰면 경사로에서 너무 느리다. 아래 1.4 참고 (확인: 실측) |

### 1.3 lazygyu 마블 룰렛 내부 (`gh api`로 소스 열람, 최근 커밋 2026-11-02)

| 항목 | 내용 (확인: 소스 읽음) |
|---|---|
| 물리 엔진 | **matter.js가 아니라 box2d-wasm**이다 (`src/physics-box2d.ts`). 중력 (0, 10), `world.Step(dt, 6, 2)` |
| 루프 | 10ms 고정 스텝. 벽시계 경과를 누적해 10ms씩 소비한다 (`roulette.ts _update`) |
| 맵 데이터 `src/data/maps.ts` | `StageDef { title, goalY, zoomY, entities[], cameraZones?, zoomZones?, progress? }`. `MapEntity { position, type: 'static'\|'kinematic', shape: box\|circle\|polyline, props: { density, restitution, angularVelocity, life? } }`. 벽은 대부분 **polyline(점 목록)** → box2d 엣지 체인. 회전 장애물은 kinematic + angularVelocity. `life`가 있으면 닿으면 사라지는 블록. 단위는 월드 미터, 맵 폭 약 26, 화면 배율 30px/단위 |

| 카메라 `camera.ts` | 목표 위치를 정하고 매 프레임 남은 거리의 1/10씩 다가간다 (`_interpolation`, delta 10). 대상 구슬 + 바로 뒤 경쟁 구슬을 한 화면에 담도록 줌(0.6~1). 순위가 바뀌어도 **20프레임 유지돼야 대상 교체**(깜빡임 방지), 교체 시 36프레임에 걸쳐 섞음. `cameraZones` 안이면 구역 전체를 보여줌 |
| 미니맵 `minimap.ts` | 왼쪽 세로 스트립. 배율 = min(4, 화면높이/goalY, 폭/맵폭). 장애물·구슬·현재 뷰포트 사각형을 그림. 마우스 올리면 그 위치를 미리보기 |
| 시뮬 스크립트 `scripts/simulate.ts` | 렌더 없이 물리만 돌려 맵별 골인 시각 분포·shake 통계를 낸다. `Math.random`을 시드 고정으로 바꿔 재현 |

### 1.4 녹화 크기 줄이기와 보간
- 좌표를 정수로 반올림하고 `[x0,y0,x1,y1,...]` 평탄 배열로 저장. 각도는 뺐다 (구슬이 원이라 안 보임)
- 실측 (확인: `--batch 300`의 30판 측정): 30fps 평균 **128KB**, gzip 44KB, 15fps 68KB. 이 중 맵 데이터 8KB, 프레임 118KB (seed 1 기준)
- 더 줄이려면: 15fps + 선형 보간 (절반), 프레임 간 차분 저장 (추정: 숫자 대부분 1~2자리라 더 작아짐), express 응답 gzip (`compression` 패키지는 npm 추가라 승인 필요). 40명 × 128KB ≈ 5MB/판이라 **줄이지 않아도 된다** (추정)
- 재생: 시각 t → `f = t × fps`, 앞뒤 프레임을 선형 보간 (`preview.html positions()`). 30fps 녹화를 120Hz 화면에서 재생해도 끊김이 안 보였다 (확인: 브라우저 스크린샷 + rAF 120프레임 중 최대 간격 8ms)

```
cd proto/구슬경마
```

## 3. 의견

### 3.1 이 방식으로 갈 만한가 → **간다**
- "서버 1회 계산 → 녹화 → 재생"이 1분 경주로 성립한다. 1등 평균 62초, 300판 중 290~300판이 55~75초 안 (확인)
- 계산은 1판 0.3~0.9초라 "마감" 버튼 뒤에 바로 계산해도 된다 (확인). 그동안 Node 이벤트 루프가 막히지만 40명 행사에선 문제없다 (추정)
- 끼임은 3초 밀기로 충분했다. 300판 중 강제 종료 0~3판 (확인)

### 3.3 위험 요소
1. **빼빼로별 물리 차이 = 확률 차이.** 속성이 조금만 달라도 우승률이 4%~27%로 벌어진다 (확인). 배당이 판돈 비율이라 게임은 깨지지 않지만, "아몬드는 절대 안 이김"이 금방 소문난다 (추정). → 물리는 동일, 차이는 색·이름만 추천
2. 경사로 막대 관통은 검증 안 됨 (위 2.5). 맵을 바꾸면 다시 batch를 돌려야 하고, 관통 검출(진행 y가 막대를 건너뛰었는지)을 넣는 게 좋다 (추정)
3. matter.js 물리는 직관과 다르다 (경사로가 이론보다 훨씬 느림). 값은 감이 아니라 batch로 맞춰야 한다 (확인: 문제 1)
4. 녹화 크기 128KB. express 기본은 gzip을 안 한다 (추정). 40명이면 괜찮다
5. 브라우저 탭이 백그라운드면 rAF가 멈춘다. 재생을 프레임 번호가 아니라 시각 기준으로 하면 돌아왔을 때 맞는 위치가 나온다 (preview가 이미 그렇게 함) (확인: 코드)
